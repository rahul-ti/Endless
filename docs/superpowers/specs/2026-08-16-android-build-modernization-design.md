# Android Build Modernization Design

## Goal

Modernize Endless Arithmetic's Android runner so the current Flutter 3.47 toolchain can produce an APK for direct installation and, later, a signed Android App Bundle for Google Play. The application must run across the latest five or six Android releases while retaining Flutter's broader supported runtime range.

## Current State and Root Cause

The Android runner was generated by an early Flutter release and mixes obsolete Android v1 and v2 embedding patterns:

- `android/app/src/main/AndroidManifest.xml` names the deleted `io.flutter.app.FlutterApplication` class.
- `MainActivity.kt` manually calls `GeneratedPluginRegistrant.registerWith`, which current Flutter applications do not require.
- The build uses Gradle 5.6.2, Android Gradle Plugin 3.5.0, Kotlin 1.3.50, `jcenter()`, compile/target SDK 28, and Flutter's legacy imperative Gradle script.

Flutter 3.47 stops the build as soon as it detects the deleted v1 application class. Removing only that reference would reveal further incompatibilities in the legacy Gradle configuration, so the Android runner must be migrated as one coherent unit.

## Compatibility Baseline

The modernized runner will use the versions supplied by Flutter 3.47:

- Minimum Android SDK: API 24 (Android 7.0)
- Compile Android SDK: API 36 (Android 16)
- Target Android SDK: API 36 (Android 16)
- Android Gradle Plugin: 9.1.0
- Gradle: 9.3.1
- Kotlin Gradle Plugin: 2.4.0
- Java source and target compatibility: Java 17

This range includes Android 12 through Android 17, the latest six releases as of August 2026. Targeting API 36 satisfies the Google Play target API requirement effective August 31, 2026, while Android's forward compatibility allows the app to run on Android 17.

## Android Runner Architecture

The Android platform files will be regenerated from the installed Flutter 3.47 Kotlin template, then reviewed rather than hand-translated from the legacy Gradle files. The migration will:

- use the declarative Flutter Gradle plugin loader and Flutter Gradle plugin;
- use Android v2 embedding exclusively;
- reduce `MainActivity` to a standard `FlutterActivity` subclass;
- use the current manifest application placeholder, exported launcher activity, normal theme metadata, and process-text query;
- use AndroidX and Maven Central;
- retain the existing launcher icons and app label unless the template supplies structurally required replacements;
- remove Eclipse-specific Android project metadata from the supported build path without overwriting unrelated user changes.

The permanent Android application ID will be `com.rahultiwari.endless`. The Kotlin source package, Gradle namespace, manifest activity resolution, and application ID will use the same identifier.

## Toolchain Setup

The Mac currently has Flutter 3.47 and Chrome but no Android SDK. Android command-line tools will be installed along with the SDK platform, build tools, platform tools, and any Flutter-required NDK version. Android licenses will be accepted, `flutter doctor -v` will confirm the toolchain, and Flutter will be configured to use the installed SDK path if automatic discovery does not find it.

The build will use a Java runtime compatible with Flutter's Gradle and Android Gradle Plugin versions. Java 17 is the configuration baseline even if a newer compatible JDK launches Gradle successfully.

## Packaging and Signing Flow

### Direct installation

The first deliverable is a debug APK produced by `flutter build apk --debug`. It uses Android's debug signing identity and can be installed directly on a device for testing. Its expected output is `build/app/outputs/flutter-apk/app-debug.apk`.

### Google Play

Before publishing, a dedicated upload keystore will be created outside version control. A local ignored `android/key.properties` file will point to that keystore, and the release Gradle configuration will load its alias and passwords without committing secrets. Google Play App Signing will manage the distribution signing key after the signed release bundle is uploaded.

The Play deliverable will be produced by `flutter build appbundle --release` at `build/app/outputs/bundle/release/app-release.aab`. The debug APK is not a Play Store artifact, and devices with the debug build installed might need that build removed before installing a differently signed release build.

## Verification

The migration is complete only after all of these checks succeed:

1. `flutter doctor -v` recognizes the Android toolchain without an Android SDK error.
2. `flutter analyze` reports no issues.
3. `flutter test` passes the full Dart and widget test suite.
4. `flutter build apk --debug` exits successfully.
5. The generated APK exists at the documented path.
6. APK manifest inspection confirms minimum SDK 24, target SDK 36, application ID `com.rahultiwari.endless`, and the expected launcher activity.
7. If a physical Android device or emulator is available, the APK installs and the arithmetic question-to-answer flow receives a runtime smoke test. Lack of a connected device does not invalidate the build artifact, but it will be reported explicitly.

The later Play-signing phase additionally requires a successful signed `flutter build appbundle --release` and bundle inspection before upload.

## Error Handling and Safety

- Existing unrelated worktree changes will be preserved.
- Generated Android changes will be diff-reviewed before verification.
- Signing credentials and keystores will never be committed.
- The current staged deletion of the tracked legacy `android/key.properties` file will remain intact.
- If Flutter's generated template differs from the documented version baseline, implementation will stop and reconcile the difference rather than silently mixing toolchain versions.

## Out of Scope

- Publishing to Google Play or changing Play Console state
- Creating store listing copy, screenshots, privacy policy, or release notes
- Supporting Android versions older than Flutter 3.47's API 24 minimum
- Changing the Flutter UI or arithmetic behavior
